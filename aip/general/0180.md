# Backwards compatibility

## Guidance

- Compatibility strength follows the path prefix ([AIP-181](./0181.md)):
  - `/vN/...` — published stable rules below apply
  - `/beta/...` and `/alpha/...` — preview/experimental; in-place breaks allowed
- On stable prefixes (`/v1`, `/v2`, …):
  - Additive changes (new optional fields, new endpoints, new enum values that
    clients can ignore) are preferred.
  - Removing fields, renaming JSON names, changing field types, or tightening
    requiredness is breaking and requires a new path prefix.
  - Changing pagination shape, error envelope, or path identity scheme is
    breaking and requires a new path prefix.
- Visibility flags do not alter these rules; hidden and public operations under
  the same prefix share that prefix's compatibility expectations.
- If an implementer drifts from an AIP, fix the implementer (or amend the AIP
  first, then the implementer). Do not leave the contract as a permanent
  exception.
