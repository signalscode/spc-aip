# Resource identity and paths

Resources are addressed by **UID string ids** on versioned, kebab-case
collection paths. Display names are separate from identity.

## Guidance

### Paths

- Collection paths **must** be plural kebab-case under the API version:
  `/beta/books`, `/v1/phone-numbers`.
- Instance paths **must** use `{id}` (or a typed sibling such as `{shelf_id}`)
  as the path parameter name. Path id segments **must** be UID strings.
- Nested resources **must** include the parent id in the path:
  `/beta/books/{id}/reviews/{review_id}`.
- Path segments **must not** use Google-style hierarchical `name` bindings
  (`{name=publishers/*/books/*}`).

### Identity fields

- Resources **must** expose a stable `id` field that is:
  - a **`{type}-{object}` UID string** on the public wire (see construction
    below)
  - not a raw sequential integer clients should parse or enumerate
  - read-only
- Resources **may** expose a human-readable `name` (display name). `name` is
  **not** the canonical resource path.
- Do **not** require clients to store hierarchical resource name strings as the
  primary identifier.
- Cross-resource references **should** use `*_id` UID string fields (for
  example `author_id`), not embedded resource objects and not public integer
  primary keys.
- Clients **must** treat the object segment as an uninterpreted token: do not
  parse, increment, or infer ordering from it. The type segment is stable for
  a given resource kind and may be used only to tell kinds apart at a glance.

### Public text construction

A public `id` or `*_id` **must** be the text form produced by `sdk/go/uid`
`Text` / `Parse`:

```text
{type}-{object}
```

Priorities (highest first):

1. Human readability and usability — short, copy/paste friendly strings with a
   stable type segment so people can tell kinds of ids apart at a glance.
2. Hide the raw object number from obvious view — not encryption. A public odd
   multiply-mod mix makes sequential row ids look unrelated so adjacent rows
   are not confused and the integer is not leaked in the clear.
3. Consistent prefix for the same type id — every id of a given type shares the
   same left-hand segment.

Encoding:

- `type` is unpadded base32 (`A–Z2–7`) of the type id as a little-endian
  `uint32`, with trailing `0x00` bytes stripped.
- `object` is unpadded base32 of `(object_id × mul) mod 2^(8w)` as
  little-endian, exactly `w` bytes. `w` is grown so the object segment is
  always at least 4 characters (2 bytes → 4 chars). `w` grows further when
  the object id needs more than 2 bytes.
- Segments are joined by a single hyphen (`-`). Base32 has no `-`, so the
  separator is unambiguous.
- `mul` is the public odd constant `0x9E3779B97F4A7C15`. The mix is reversible
  and is UX opacity, not a security boundary.
- Text is case-insensitive: producers emit uppercase; parsers accept any case
  of `A–Z` / `a–z` with digits `2–7`.

The type id packing is unchanged:

- Bits 31–16 are the module type. `0` names the module and is not an object
  type. Object types are `1..65535`.
- Bits 15–12 are the version nibble (`version & 0xF`). Nibble `0` is invalid.
- Bits 11–0 are the module id, `1..4095`. Module `0` is never assigned.

The object id **must** be the resource's positive internal integer key. Zero
and negative values are invalid. The type id is part of the value, so an id is
unique across resource types, not only inside one collection.

A decoder **must** require that alphabet, no `=` padding, exactly one `-`
separator, a valid type id, module type ≠ `0`, an object id greater than 0, a
width that matches the decoded object id, and a re-encode that equals the
canonical (uppercase) form. An id that decodes as a different resource type is
not an id of the resource being addressed.

Binary codecs (12-byte big-endian TypeID‖ObjectID) are a separate form for
fixed-width blobs. Producers **must** put only the `{type}-{object}` text on
the public HTTP wire.

OpenAPI **should** set `minLength` 10, `maxLength` 21, and `pattern` to
`^[A-Za-z2-7]+-[A-Za-z2-7]{4,}$`. That pattern checks shape. The decoder
rules above still apply.

Worked example: type id `135173` (module `5`, module type `2`, version nibble
`1`) and object id `1001` encode as `AUIAE-DUXA`. Object id `1002` of the same
type encodes as `AUIAE-GKVA` (same prefix; unrelated-looking object segment).

### Examples

```http
GET /beta/books/AUIAE-DUXA
GET /beta/books/AUIAE-DUXA/settings
POST /beta/books/AUIAE-DUXA:clone
```

```json
{
  "id": "AUIAE-DUXA",
  "name": "Les Misérables",
  "author_id": "AQIAC-DUXA",
  "created_timestamp": "2021-01-01T00:00:00Z"
}
```
