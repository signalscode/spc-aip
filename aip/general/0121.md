# Resource-oriented design

Public APIs are modeled as resources (nouns) with a small set of standard
methods, plus custom methods when standards do not fit.

## Guidance

- Model the API as collections of resources under a version prefix
  (`/beta/...`, `/v1/...`, `/v2/...`; see [AIP-181](./0181.md)).
- Prefer standard methods ([Get](./0131.md), [List](./0132.md),
  [Create](./0133.md), [Update](./0134.md), [Delete](./0135.md)) over custom
  methods ([AIP-136](./0136.md)).
- Nested resources use parent collection paths, for example
  `/beta/books/{id}/reviews/{review_id}`.
- Singleton sub-resources (for example settings) live on a fixed path without a
  child id (see [AIP-156](./0156.md)).
- The resource schema returned by Get/List/Create/Update for the same resource
  **must** be consistent.
- Incomplete CRUD is allowed when product semantics require it (for example
  List/Get/Delete only). Document why Create or Update is omitted.

### Methods and HTTP

| Method | HTTP | Path shape |
| ------ | ---- | ---------- |
| List | `GET` | `/beta/{collection}` |
| Get | `GET` | `/beta/{collection}/{id}` |
| Create | `POST` | `/beta/{collection}` → **201** |
| Update | `PATCH` | `/beta/{collection}/{id}` |
| Replace | `PUT` | singleton or association paths (see AIP-134 / AIP-156) |
| Delete | `DELETE` | `/beta/{collection}/{id}` → **204** |
| Custom | usually `POST` | `/beta/.../{id}:custom-verb` (see [AIP-136](./0136.md)) |

### Example

```http
GET    /beta/books
POST   /beta/books
GET    /beta/books/AUIAE-DUXA
PATCH  /beta/books/AUIAE-DUXA
DELETE /beta/books/AUIAE-DUXA
POST   /beta/books/AUIAE-DUXA:clone
PUT    /beta/books/AUIAE-DUXA/settings
```
