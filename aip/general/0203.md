# Field behavior documentation

## Guidance

Document field optionality in the OpenAPI schema, not via implementer-only
conventions:

| Behavior | OpenAPI representation |
| -------- | ---------------------- |
| Required on write/read | listed in `required`; no `readOnly` |
| Optional on write | omitted from `required`; may be nullable if clearing is allowed |
| Read-only | `readOnly: true` (and usually omitted from request schemas) |

- **TODO:** Update / PATCH clearing and nullability rules are **undecided**.
  See the large TODO in [AIP-134](./0134.md#todo--patch-field-semantics-undecided).
  Do not invent a permanent clear/null model here until that TODO is resolved.
- `id` and server timestamps **must** be read-only.
- Adding newly required fields to an existing published request body is
  breaking.

### Example

```yaml
CreateBookRequest:
  type: object
  required: [name]
  properties:
    name:
      type: string
      description: Display name for the book.
      example: Les Misérables
    title:
      type: string
      description: Optional subtitle.
      example: A Novel

UpdateBookRequest:
  type: object
  properties:
    name:
      type: string
      description: New display name. Omit to leave unchanged.
    title:
      type: string
      nullable: true
      description: >
        New subtitle. Omit to leave unchanged; send null to clear.

Book:
  type: object
  required: [id, name, created_timestamp]
  properties:
    id:
      type: string
      readOnly: true
      description: Opaque public identifier.
      example: BRAC_HS4_ug
    name:
      type: string
    title:
      type: string
      nullable: true
    created_timestamp:
      type: string
      format: date-time
      readOnly: true
```
