# Field behavior documentation

## Guidance

Document field optionality in the OpenAPI schema, not via implementer-only
conventions:

| Behavior | OpenAPI representation |
| -------- | ---------------------- |
| Required on write/read | listed in `required`; no `readOnly` |
| Optional on write | omitted from `required`; nullable when JSON `null` clears it, or resets it to a documented default, on Update |
| Read-only | `readOnly: true` (and usually omitted from Create/Replace/Update request schemas) |

- Response fields **should** be required and always present in the JSON body.
  A missing key is discouraged and permitted only when omission has a
  documented reason, for example a field returned only when the request asks
  for it. A nested response object **may** be omitted, rather than sent as
  `null`, when it is empty and sending it would bloat the response. Document
  that omission. Do not use `null` for that field.
- A zero value **must not** mean the value is unavailable. `""`, `0`, and
  `false` are valid only when they are real stored values. Unavailable is
  JSON `null`: the field is present, and `null` is the only unavailable
  state. An empty array is an empty list, not unavailable: return `[]`, not
  `null` and not a missing key. On Create and Replace, omit and JSON `null`
  may both mean unavailable for an optional field; `""` must not.
- A request schema **must not** reuse a response schema when a field is
  optional on the request and required on the response. Define a separate
  request type.
- Partial Update uses [JSON Merge Patch](https://datatracker.ietf.org/doc/html/rfc7396)
  ([AIP-134](./0134.md)): omit = leave unchanged, non-null value = set,
  `null` = remove. For an array, `null` clears it, and `null` and `[]` are
  equivalent. OpenAPI Update request schemas **should** document that
  shape (resource-like object; clearable fields marked `nullable: true`).
- A field that is always stored and has one fixed default **may** treat omit
  and JSON `null` as that default on Create and Replace. On Update, omit
  leaves the current value and JSON `null` resets to that default instead of
  removing the member ([AIP-134](./0134.md)). The field doc **must** name the
  default. The response returns the stored value, not null.
- Do **not** invent a separate tri-state type beyond omit / value / `null`
  unless a field cannot use merge-patch `null` for clear (document that
  exception on the field).
- `id` and server timestamps **must** be read-only and **must not** be
  meaningful Update patch members.
- Adding newly required fields to an existing published Create/Replace request
  body is breaking.

### Example

```yaml
CreateBookRequest:
  type: object
  required: [name]
  properties:
    name:
      type: string
      description: Display name for the book.
      example: Les Misérables
    title:
      type: string
      description: Optional subtitle.
      example: A Novel

UpdateBookRequest:
  type: object
  description: >
    JSON Merge Patch body (RFC 7396). Omit a member to leave it unchanged;
    send null to remove an optional member.
  properties:
    name:
      type: string
      description: New display name. Omit to leave unchanged.
    title:
      type: string
      nullable: true
      description: >
        New subtitle. Omit to leave unchanged; send null to clear.

Book:
  type: object
  required: [id, name, title, created_timestamp]
  properties:
    id:
      type: string
      readOnly: true
      description: Opaque public identifier.
      example: AUIAE-DUXA
    name:
      type: string
    title:
      type: string
      nullable: true
      description: Subtitle. Null when the book has none. An empty string is not used.
    created_timestamp:
      type: string
      format: date-time
      readOnly: true
```
